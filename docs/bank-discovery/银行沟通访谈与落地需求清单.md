# 银行沟通访谈与落地需求清单

版本：V0.1（会前草案）  
项目：基于多智能体协同的银行外包供应商动态风险预测与决策系统  
发起人：李芳痕及项目组  
适用场景：与九江银行内部业务、科技、风险、安全或外包管理人员进行首次需求访谈  
当前定位建议：`G2 受控小范围试用`，待项目组与银行确认

> 这不是一份“向银行索取全部数据”的清单。建议先听完一个真实业务案例，再根据银行允许的范围索取数据字典和少量脱敏样本。任何真实数据使用、模型调用和对外操作都以银行授权为前提。

## 一、我们希望这次沟通得到什么

这次会议不是为了证明现有原型已经可以在银行正式上线，而是为了共同确认四件事：

1. 银行现在最想解决的外包供应商风险问题是什么；
2. 风险从出现苗头到被发现、上报、处置，目前是怎样流转的；
3. 哪些数据确实存在、由谁管理、能否在脱敏后用于测试；
4. 第一阶段做到什么程度，银行才愿意安排少量人员试用。

会后最理想的结果不是拿到大量原始数据，而是形成：

- 1 个从风险发生到处置结束的脱敏真实案例；
- 3 个银行最希望系统解决的业务场景，并排出先后顺序；
- 1 份数据目录或数据字典；
- 1 份人员、权限和人工审核流程；
- 1 个小范围试用的允许边界和验收方式。

## 二、建议开场白（可直接照读）

> 我们目前已经做出一个使用模拟数据的可运行原型。它能够整理供应商历史事件，计算未来一段时间的风险升级参考概率，检查证据是否完整，再给工作人员提供候选建议。系统不会自动处罚供应商，也不会代替银行人员作最终决定。
>
> 今天我们不想先用技术方案限制真实业务，希望先听您讲一个实际发生过的供应商风险案例：最早出现了什么苗头，谁先发现，信息从哪里来，最后由谁决定怎么处理。我们再根据这个流程确认系统应该帮在哪一步，以及需要哪些数据。涉及真实信息时，只需要讲脱敏后的情况，不需要提供客户身份、账号、密码或其他敏感内容。

## 三、先让银行讲清楚一个真实案例

请邀请对方选择一个已经结束、可以脱敏讨论的案例，例如服务中断、项目严重延期、关键人员流失、安全漏洞、违规外包或供应商经营异常。

按时间顺序提问，尽量不要一开始使用“特征、标签、RAG、Agent”等词。

| 顺序 | 建议提问 | 我们真正需要了解的内容 |
|---|---|---|
| 1 | 这件事最早是什么异常？是谁先注意到的？ | 风险的第一信号及发现人 |
| 2 | 当时信息来自工单、邮件、会议、监控还是外部消息？ | 数据来源和载体 |
| 3 | 从第一条异常到确认风险，大约经过多久？ | 系统需要提前多久提醒 |
| 4 | 哪些后续信号让大家确认“不是普通波动”？ | 真正有判断价值的组合信号 |
| 5 | 当时谁需要被通知？谁有权决定下一步？ | 使用者、审核人和权限 |
| 6 | 最终采取了观察、整改、升级汇报还是其他措施？ | 系统允许提出的候选建议 |
| 7 | 哪些材料必须齐全才能作决定？ | 证据通过条件 |
| 8 | 如果当时系统提前提醒，提前几天或几周最有价值？ | 预警时间窗口 |
| 9 | 如果提醒错了会带来什么麻烦？漏掉风险又会怎样？ | 误报和漏报哪一种更不能接受 |
| 10 | 处置完成后，怎样判断供应商已经恢复正常？ | 风险关闭及反馈标准 |

需要追问的失败情况：

- 信息不完整时，现在是谁补充、等多久、是否允许继续判断；
- 不同部门给出的信息互相矛盾时，以谁为准；
- 同一事件重复上报时，如何确认是不是同一件事；
- 风险处理到一半，基础数据发生变化时，是否需要重新审核；
- 系统或外部数据暂时不可用时，业务是否必须继续依靠人工流程。

## 四、需要银行确认的真实业务需求

### 4.1 谁使用，在哪一步使用

请银行确认主要使用者可能包括哪些岗位：

- 外包供应商管理人员；
- 科技项目或系统负责人；
- 操作风险、合规或审计人员；
- 信息安全人员；
- 负责最终复核或审批的管理人员。

每类人员分别确认：能看什么、能修改什么、能审核什么、不能看什么。

### 4.2 系统最值得帮助的环节

请对以下能力排出前三名，不要求第一阶段全部实现：

- 把分散在多个系统和文件里的供应商风险信息汇总起来；
- 发现风险分、故障、延期或人员变化的持续恶化；
- 提前提醒未来几周可能升级的供应商；
- 自动整理风险依据，减少人工翻查材料；
- 根据制度给出候选处置建议；
- 跟踪整改是否按期完成；
- 生成管理报告或审计留痕；
- 复盘过去风险案例，检查当时是否存在可提前发现的信号。

### 4.3 什么结果才算有用

不要先承诺一个准确率数字，请银行从真实工作量出发回答：

- 每周有多少家供应商需要人工查看；
- 系统最多把范围缩小到多少家，工作人员才有时间复核；
- 高风险提醒最晚要提前多久；
- 一条提醒至少要带哪些证据才能被采用；
- 哪种错误即使很少发生，也会阻止试用；
- 谁负责确认试用是否达标。

## 五、数据需求清单

### 5.1 数据获取原则

建议按以下顺序推进：

1. 先提供数据目录和字段说明，不传真实记录；
2. 再提供 10–20 家供应商的脱敏样本，覆盖正常和风险案例；
3. 样本验证完成后，再讨论受控环境中的扩大测试；
4. 若数据不得离开银行内网，模型和系统应进入获批环境运行；
5. API Key、密码、客户身份信息、账号和生产连接串不得进入样本、提示词或 GitHub。

### 5.2 第一优先级：必须了解的数据

| 数据类别 | 希望包含的内容 | 用普通话解释用途 | 需要银行确认 |
|---|---|---|---|
| 供应商基本信息 | 统一编号、名称或脱敏名称、服务类别、状态 | 确认每条事件到底属于哪家供应商 | 由哪个系统维护，编号是否统一 |
| 合同信息 | 合同编号、开始/结束时间、重要程度、服务范围 | 判断供应商承担了什么责任、影响有多大 | 哪个版本算正式合同状态 |
| 项目和系统信息 | 项目、系统、系统重要程度、负责人 | 同样的故障，核心系统和普通系统影响不同 | 系统重要程度由谁认定 |
| 风险事件 | 事件编号、发生时间、类别、严重程度、来源、处理状态 | 让系统看到发生过什么，并能回到原始证据 | 事件编号是否唯一，类别标准是什么 |
| 服务质量/SLA | 达标率、违约次数、响应和恢复时间 | 发现服务能力是否持续下降 | 更新频率和正式统计口径 |
| 工单和故障 | 工单等级、发生/恢复时间、是否重复、影响范围 | 发现故障是否变多、变严重 | 哪些工单允许用于风险研判 |
| 整改记录 | 整改编号、问题、开始/截止/完成时间、验收结论 | 判断问题是否真的解决、是否反复发生 | 谁确认整改完成 |
| 历史研判结果 | 当时判断、审批、最终是否升级、处置结果 | 作为模型学习和效果检验的“参考答案” | 谁的结论算正式、能否回溯修改 |

### 5.3 第二优先级：提升提前预警能力的数据

| 数据类别 | 希望包含的内容 | 可能提供的提前信号 |
|---|---|---|
| 项目交付 | 里程碑、延期天数、延期次数、质量问题 | 风险出现前的交付恶化 |
| 人员情况 | 人员数量、关键岗位缺口、核心人员变动 | 服务团队可能失去履约能力 |
| 安全情况 | 漏洞、补丁、测评问题、关闭时限 | 安全风险是否持续暴露 |
| 合规和审计 | 检查问题、监管问询、整改期限 | 合规问题是否升级 |
| 经营和财务 | 经营异常、司法风险、信用变化 | 供应商持续经营能力变化 |
| 舆情和投诉 | 已核验的负面信息、投诉趋势 | 外部风险的早期苗头 |
| 集中度和替代性 | 同类服务供应商数量、替换难度 | 判断风险一旦发生有多难处理 |

这些字段不是越多越好。只有银行认为它与真实判断有关、来源可信、用途获批，才进入模型。

### 5.4 每一类数据都要同时问清八件事

1. 数据由哪个部门和系统产生；
2. 谁是正式负责人，发生冲突时以谁为准；
3. 多久更新一次，允许使用多旧的数据；
4. 能覆盖多少供应商和多长时间；
5. 缺失、重复或错误大概有多少；
6. 是否包含敏感信息，允许在哪个环境使用；
7. 用什么编号把供应商、合同、项目、系统、事件和整改连接起来；
8. 数据不能获取或暂时中断时，系统应该停止、使用旧数据并提示，还是转人工。

### 5.5 第一轮建议交付物

第一轮不要求银行直接交付生产库，建议先请求：

- 数据表目录；
- 字段名、字段含义、类型、示例和是否允许为空；
- 各数据来源和更新频率；
- 脱敏规则；
- 10–20 家供应商的脱敏样本；
- 至少 3 个风险案例和 3 个正常案例；
- 每个案例的正式结论和可引用证据编号。

## 六、真实风险预警全过程

```text
银行业务系统产生数据
        ↓
检查数据是否完整、是否属于同一供应商、是否过期
        ↓
把工单、合同、系统、人员、整改等信息按供应商和时间连接
        ↓
固定规则先检查明确红线
        ↓
预测模型判断未来一段时间是否可能升级
        ↓
大模型读取已获批制度和材料，整理原因与候选建议
        ↓
证据检查：来源、时间、归属、完整性
        ↓
银行工作人员查看、补充、驳回或确认
        ↓
进入现有整改/报告流程，不由系统自动处罚或中止合同
        ↓
记录最终结果，用于复盘和下一版本评估
```

各技术部分的普通话解释：

| 技术名称 | 普通话解释 | 在本项目里的边界 |
|---|---|---|
| 数据校验 | 先确认材料没有对错人、缺字段或时间写反 | 数据有问题时停止计算并说明原因 |
| 特征 | 把很多历史记录整理成可比较的数字，如近四周故障次数 | 只能使用当时已经发生的信息 |
| 预测模型 | 根据过去案例找规律，输出风险升级参考概率 | 不替代正式风险等级和人工判断 |
| 大模型 | 擅长读文字、归纳制度、整理说明 | 不直接计算风险分，不拥有处置权 |
| RAG 知识库 | 先找出相关制度原文，再让大模型据此说明 | 只检索经银行批准的材料，并保留出处 |
| Agent | 一个职责明确的软件步骤 | 不能越过固定规则或权限 |
| 多 Agent 调度 | 按固定顺序让不同步骤接力 | 证据不通过就不能进入候选处置 |
| 人工复核 | 由有权限的人确认最终结论 | 高影响决定必须保留这一关 |

## 七、大模型落地时要向银行问清的内容

大模型建议先只承担“制度检索、材料摘要、风险说明草稿”，不要承担正式风险定级或自动处置。

请银行确认：

- 数据是否允许调用互联网模型，还是必须在银行内网或指定环境运行；
- 哪些字段必须在发送给模型前删除或替换；
- 模型服务方是否允许保存输入输出，保存多久；
- 哪些制度文件可进入知识库，哪个版本有效；
- 回答没有依据时，是明确说“不知道”还是转人工；
- 大模型超时、余额不足或服务中断时，业务能否继续使用规则和预测模型；
- 谁负责审核提示词、模型版本和输出质量；
- 是否需要保留“使用了哪份数据、制度、模型和提示词”的记录。

不可接受的行为：

- 编造不存在的事件编号或制度条款；
- 引用其他供应商或未来时间的数据；
- 把参考概率说成银行正式结论；
- 未经人工确认，直接发出处罚、停服或合同变更指令；
- 把真实密钥、客户信息或未获批材料发送到外部模型。

## 八、建议采用的落地阶段

### 阶段 0：明确试用边界

共同确认使用人员、允许的数据、运行环境、禁止动作和数据负责人。建议当前目标为“受控小范围试用”，只辅助指定人员，不自动改变外部系统。

完成标志：银行和项目组明确写下“可以做什么、不能做什么、谁负责”。

### 阶段 1：真实流程复盘

用至少一个脱敏案例还原“异常出现—发现—上报—判断—处置—关闭”的过程。

完成标志：系统要帮助的环节、预警时间和证据要求明确。

### 阶段 2：数据盘点与脱敏样本

先拿数据字典，再在获批环境中使用少量样本做完整性和关联检查。

完成标志：每项数据有来源、负责人、用途、更新时间、连接编号和缺失处理方式。

### 阶段 3：历史回放

让系统只看案例当时已经存在的数据，检查能否比现有人工流程更早发现问题。严禁使用事后结论或案例编号里的答案信息。

完成标志：对正常、渐进、突发、整改恢复等案例分别报告命中、误报和漏报，不只展示最好成绩。

### 阶段 4：制度知识库与大模型辅助

导入经批准的制度版本，让大模型基于制度和证据生成说明草稿；同时保留无大模型时的固定流程。

完成标志：每段关键结论能追到制度或证据；无依据时会停止或转人工。

### 阶段 5：影子运行

系统在后台产生结果，但不影响工作人员原有决定。事后比较系统提示和实际处置。

完成标志：连续一段约定时间记录效果、响应时间、错误和人工采用情况，没有自动外部动作。

### 阶段 6：受控小范围试用

允许指定人员在页面查看、补充和确认结果。所有高影响建议仍需人工审批，并可追溯谁在何时作了什么决定。

完成标志：达到银行确认的业务、数据、安全和操作验收要求，并能在故障时回到人工流程。

### 阶段 7：是否生产化，由银行重新评审

生产化不是“试用效果不错就直接开放”。还需单独确认容量、稳定性、备份恢复、监控告警、版本回滚、支持人员和安全检查。

完成标志：业务、数据、安全、科技运维和项目负责人分别签字确认。

## 九、当前原型要如实说明的状态

已完成：

- 使用 200 家供应商、52 周模拟数据跑通数据处理和预测流程；
- 使用固定流程调度风险识别、关联分析、动态预测、证据核验、候选建议和人工复核；
- 能阻止引用未来证据或其他供应商证据；
- 能在本地训练三种基线模型并生成评估报告；
- 已预留 OpenAI 兼容的大模型调用接口和本地知识库能力。

尚未完成或不能承诺：

- 现有模拟数据的后段预测效果不足，不能称为真实业务准确率；
- 尚无银行真实数据、正式规则和已授权制度材料；
- 关联分析和候选处置目前仍是演示规则；
- 大模型尚未进入 Agent 主流程；
- 前后端接口、权限、日志和运行环境仍需团队及银行确认；
- 系统不能用于自动处罚、自动停服或替代银行人员决策。
