# 风险算法迭代与回滚说明

## 现在采用的处理方式

系统不再把所有风险混成一个问题，而是分成三条线：

1. **渐进升级**：根据截至本周已经发生的事件、风险分变化、整改、合同和系统重要性，预测未来 1—3 周是否升级；
2. **当周突发红线**：本周一旦出现严重程度 4—5 的事件，立即触发红线检查。它是实时发现，不冒充提前预测；
3. **整改恢复**：处于整改期且风险分下降时，标记恢复趋势，供人工判断整改是否有效。

## 一次训练如何验证

候选模型依次经历以下步骤：

1. 用第 1—22 周训练、第 23—26 周验证；
2. 用第 1—26 周训练、第 27—30 周验证；
3. 用第 1—30 周训练、第 31—34 周验证；
4. 综合三个窗口的平均效果和稳定程度选模型；
5. 用三个验证窗口的“过去预测结果”校准概率，并按 F2 选择阈值，优先减少漏报；
6. 冻结第 35—44 周，只在最后做一次放行检查。

测试集不用于调参数。如果多次查看同一测试集再修改算法，它就不再是可靠的“闭卷考试”。正式落地时应按月向后滚动，并保留一个银行内部盲测时间段。

## 晋级和回滚

训练先生成 `candidate_*` 文件。只有候选模型同时满足 PR-AUC、召回率和准确率不明显低于现用模型时，才复制为 `champion.joblib`。晋级前会保存旧模型、旧指标、旧元数据和旧 SHAP 解释。

```powershell
python -m app.main train
python -m app.main rollback-model
```

如果候选未通过，状态记为 `REJECTED_KEEP_INCUMBENT`，现用模型不变。回滚会恢复最近一套完整快照，并在 `model_registry.json` 留下执行时间。

## 本轮结果

本轮使用 XGBoost 作为候选冠军：

| 指标 | 旧模型 | 新模型 |
|---|---:|---:|
| 测试 PR-AUC | 0.0309 | 0.0858 |
| 召回率 | 10.0% | 25.0% |
| 准确率（预警命中率） | 6.35% | 17.86% |
| 命中风险 | 4 | 10 |
| 漏掉风险 | 36 | 30 |
| 误报 | 59 | 46 |

新模型通过当前技术门槛，但还不能称为银行生产可用。分场景结果显示：渐进积累型样本可以识别，测试期 30 条突发型风险仍全部漏掉。根因是现有模拟数据在突发前没有可观察信号，而不是继续堆模型就能解决。

## 下一轮最有价值的数据

按优先级补充：SLA 达标率和违约次数、交付延期变化、关键人员离职或缺口、投诉与工单异常、系统可用性下降、舆情早期信号。每项都要带供应商、发生时间、采集时间和数据来源，确保模型当时确实看得到。

不得把供应商编号中的案例类型、未来事件或人工答案作为输入特征。编号前缀只允许用于测试后分场景统计。
